# `matmul_morton_avx2` — Resumen conceptual

## 1. Idea general

`matmul_morton_avx2` mantiene la **misma estructura recursiva** de `matmul_morton` (Fase 1.6) pero cambia dos cosas:

1. El layout de $A$ pasa de **Morton-de-elementos** a **Morton-de-bloques** con tile = 4.
2. La hoja deja de ser un kernel ijk escalar y pasa a invocar un **microkernel AVX2 + FMA** de geometría $4 \times 16$.

La motivación es la misma que `tiled_ikj_avx2`: la recursión sola resuelve el problema de memoria, pero la hoja escalar deja al procesador haciendo 1 multiplicación por ciclo cuando podría hacer 32.

| Problema | Resuelve | Herramienta |
|---|---|---|
| Memoria | traer datos a cache antes de usarlos | recursión Z-order (cache-oblivious) |
| Cómputo | consumir esos datos a máxima velocidad | microkernel AVX2 + FMA en hoja |

Ninguna funciona bien sin la otra.

---

## 2. El layout Morton-de-bloques

**Morton-de-elementos** (Fase 1.6):
$$A[i, j] \to A_{\text{morton}}[\text{morton\_encode}(i, j)]$$

**Morton-de-bloques** (Fase 1.7) con $\text{MR} = 4$:
$$A[i, j] \to A_{\text{morton}}\bigl[\text{morton\_encode}(i / \text{MR},\ j / \text{MR}) \cdot \text{MR}^2 + (i \bmod \text{MR}) \cdot \text{MR} + (j \bmod \text{MR})\bigr]$$

Es decir: $A$ se particiona en sub-bloques de $\text{MR} \times \text{MR} = 4 \times 4$ floats; los sub-bloques se ordenan entre sí en Z-order; los 16 floats de cada sub-bloque viven contiguos en row-major.

### Por qué no Morton-de-elementos también para la hoja

El microkernel necesita **filas contiguas** de $A$ para hacer `_mm256_broadcast_ss` de un elemento por vez. Con Morton-de-elementos, dos elementos consecutivos en una fila ($A[i, j]$ y $A[i, j+1]$) están separados por dos posiciones en memoria, no por una — el broadcast tendría que recorrer un strided scan. Empacar tiles de 4×4 en row-major restaura el stride-1 dentro del tile sin sacrificar la contigüidad de cuadrantes.

### La contigüidad de cuadrantes sigue valiendo

Al dividir un sub-bloque cuadrado de lado $2h$ en sus cuatro cuadrantes de lado $h$, los cuadrantes siguen ocupando cuatro segmentos consecutivos en `A_morton`, ahora de tamaño $h^2$ floats cada uno (en la escala de bloques). Lo único que cambia respecto a la Fase 1.6 es **el significado del nivel más bajo**: un "elemento" Morton es un tile 4×4 de floats, no un float suelto.

La reorganización la hace `reorganize_to_morton_blocks(A, A_morton, m)` una sola vez por matriz, fuera del benchmark.

## 3. Hiperparámetros

### MR = 4 y NR = 16 — geometría del microkernel

Determinados por la cantidad de registros YMM disponibles. El Zen 2 tiene 16 registros YMM nombrados (renombrados sobre un PRF de 168 entradas). La desigualdad para que C viva entero en registros:

$$\underbrace{\text{MR} \cdot \frac{\text{NR}}{8}}_{\text{acumuladores}} + \underbrace{\frac{\text{NR}}{8}}_{B} + \underbrace{1}_{A\ \text{broadcast}} \leq 16$$

Con $\text{NR} = 16$ esto da $\text{MR} \cdot 2 + 2 + 1 \leq 16 \Rightarrow \text{MR} \leq 6.5$. La Fase 1.7 elige $\text{MR} = 4$ (no 6) por dos razones:

1. **Compatibilidad con la recursión Z-order**: las divisiones por 2 a profundidad recursiva deben mantener $\text{m\_block}$ múltiplo de $\text{MR}$. Con $m$ potencia de 2 y $\text{MR} = 4$, eso se cumple trivialmente; con $\text{MR} = 6$ no.
2. **Espacio para A en registros**: con $\text{MR} = 4$ quedan **4 broadcasts simultáneos** de $A$ en registros distintos, sin reusar. El microkernel saca esos 4 elementos antes del bloque FMA — quita la dependencia entre el broadcast y el FMA siguiente.

NR = 16 porque cada fila de B son 16 floats = 2 registros YMM (8 floats por YMM).

### Balance de registros con MR = 4, NR = 16

```
c00..c31  →   8 YMMs  (acumuladores de C, viven todo el loop kc)
b0, b1    →   2 YMMs  (fila de B, se renuevan cada p)
a0..a3    →   4 YMMs  (broadcasts de A, uno por fila del tile)
─────────────────────
              14 de 16 registros YMM usados
```

Comparar con el `tiled_ikj_avx2` (Fase 1.4): allí MR=6, 12 acumuladores + 2 b + 1 a = 15/16. Aquí MR=4, 8 acumuladores + 2 b + 4 a = 14/16. El tiled empaca más C por iteración; el Morton empaca más A.

### Threshold de recursión

```c
extern size_t g_recursion_threshold_avx2;   /* default 524288 */
void matmul_morton_avx2_set_threshold(size_t threshold);
```

**Default $64 \cdot 64 \cdot 128 = 524288$ elementos producto**. A esta profundidad el panel de A activo es $64 \times 64 \times 4 = 16$ KiB, la mitad del L1d (32 KiB). Lo separa de `g_recursion_threshold` (Fase 1.6, 131072) porque los dos regímenes son distintos: la hoja AVX2 amortiza una superficie mucho mayor que el ijk escalar, así que tolera sub-bloques mayores.

### Resumen

| Parámetro | Valor | Lo fija | Apunta a |
|---|---|---|---|
| MR | 4 | geometría del ISA + recursión Z-order | registros YMM |
| NR | 16 | geometría del ISA | registros YMM |
| Threshold | 524288 | tamaño del L1d | L1d (32 KiB) |
| MORTON_AVX2_TILE | MR = 4 | layout Morton-de-bloques | row-major dentro del tile |

## 4. La hoja: `kernel_base_morton_avx2`

```c
static void kernel_base_morton_avx2(
    scalar_t *C, const scalar_t *A_morton, const scalar_t *B,
    size_t m_block, size_t k_block, size_t n_block,
    size_t a_morton_offset, size_t a_block_dim,
    size_t ldc, size_t ldb,
    scalar_t *A_local_scratch)
{
    materialize_a_panel(A_morton, ..., A_local_scratch, m_block, k_block);

    /* zero C tile */
    for i,j: C[i*ldc + j] = 0;

    /* dispatch microkernel sobre cada tile 4x16 */
    for (ii = 0; ii < m_block; ii += MR)
        for (jj = 0; jj < n_block; jj += NR)
            kernel_avx2_4x16(&C[ii*ldc + jj], ldc,
                             &A_local[ii*k_block], k_block,
                             &B[jj], ldb, k_block);
}
```

Tres fases:

### Fase 4.1: `materialize_a_panel` — Morton-de-bloques → row-major

El microkernel quiere ver $A$ como un buffer row-major **plano**: fila $i$ contigua, paso `lda = k_block` entre filas. El layout Morton-de-bloques no le sirve directamente porque dos filas dentro del mismo tile están separadas por 4 floats, pero dos filas en tiles diferentes están separadas por un salto Morton.

`materialize_a_panel` copia el sub-bloque activo de $A_{\text{morton}}$ al buffer `A_local` recorriendo los tiles en orden Morton y dentro de cada tile copiando los 4 floats row-major. El costo es $O(m_{\text{block}} \cdot k_{\text{block}})$ — lineal en el tamaño del panel, despreciable frente a los $O(m_{\text{block}} \cdot k_{\text{block}} \cdot n_{\text{block}})$ FMAs del microkernel.

El scratch `A_local` se aloja una sola vez en el wrapper público (`matmul_morton_avx2`) y se pasa como parámetro a través de toda la recursión — **ninguna hoja hace `malloc`**.

### Fase 4.2: zerear el tile de $C$

El microkernel **acumula**: $C \mathrel{+}= A \cdot B$. Para que la hoja en su variante overwrite produzca exactamente $C = A \cdot B$, hay que dejar $C$ en cero antes de invocarlo. La variante `_add` simplemente omite este paso.

### Fase 4.3: dispatch sobre tiles 4×16

Loop doble que recorre el tile $(m_{\text{block}}, n_{\text{block}})$ en pasos de $(\text{MR}, \text{NR})$. Cada llamada al microkernel computa un tile $4 \times 16$ de $C$ acumulando $\text{MR} \times k_{\text{block}}$ de $A$ y $k_{\text{block}} \times \text{NR}$ de $B$.

## 5. Microkernel `kernel_avx2_4x16`

Definido en [`kernel_avx2_morton.h`](../src/microkernels/kernel_avx2_morton.h) como `static inline`. Tres fases:

### Fase 5.1: cargar C en registros (una sola vez)

```c
c00 = loadu(&C[0 * ldc + 0]);   c01 = loadu(&C[0 * ldc + 8]);
c10 = loadu(&C[1 * ldc + 0]);   c11 = loadu(&C[1 * ldc + 8]);
c20 = loadu(&C[2 * ldc + 0]);   c21 = loadu(&C[2 * ldc + 8]);
c30 = loadu(&C[3 * ldc + 0]);   c31 = loadu(&C[3 * ldc + 8]);
```

El tile $4 \times 16$ se parte en 8 vectores (2 YMM por fila × 4 filas).

Se usa `_mm256_loadu_ps` y no `_mm256_load_ps` porque las hojas Morton no aterrizan siempre en direcciones múltiplo de 32 bytes — los offsets navegan a posiciones de elemento, no de línea de caché. La penalización de `loadu` sobre datos accidentalmente alineados es de 0 ciclos en Zen 2; usar `load` con datos desalineados sería un fault.

### Fase 5.2: loop kc (el trabajo real)

Por cada paso `p`:

```c
b0 = loadu(&B[p * ldb + 0]);          /* fila p de B, cols 0..7   */
b1 = loadu(&B[p * ldb + 8]);          /* fila p de B, cols 8..15  */

a0 = broadcast_ss(&A[0 * lda + p]);   /* A[0,p] replicado en 8 lanes */
a1 = broadcast_ss(&A[1 * lda + p]);
a2 = broadcast_ss(&A[2 * lda + p]);
a3 = broadcast_ss(&A[3 * lda + p]);

c00 = fmadd(a0, b0, c00);  c01 = fmadd(a0, b1, c01);
c10 = fmadd(a1, b0, c10);  c11 = fmadd(a1, b1, c11);
c20 = fmadd(a2, b0, c20);  c21 = fmadd(a2, b1, c21);
c30 = fmadd(a3, b0, c30);  c31 = fmadd(a3, b1, c31);
```

Por cada paso `p`: **8 FMAs × 8 floats = 64 floats de C actualizados** con solo 2 loads de B y 4 broadcasts de A. C nunca toca memoria durante todo el loop.

Las 8 FMAs son independientes entre sí (no hay dependencia RAW dentro de la iteración) — el Zen 2 las pipelinea en sus 2 unidades FMA a $2 \times 8 = 16$ flops/ciclo sostenido. En 4 ciclos retira las 8 FMAs.

### Fase 5.3: guardar C de vuelta (una sola vez)

```c
storeu(&C[0 * ldc + 0], c00);   storeu(&C[0 * ldc + 8], c01);
/* ... idem hasta c31 */
```

## 6. Por qué `static inline`

Idéntico razonamiento al de `kernel_avx2_tiled` (Fase 1.4): si el microkernel fuera función normal en un `.c` separado, el ABI obligaría a spillear los 8 acumuladores YMM al stack en cada invocación. Con `static inline` el compilador pega el código directamente en el loop de la hoja, los acumuladores nunca salen de los registros.

- **`inline`** → el compilador pega el código directamente en el loop `ii × jj`.
- **`static`** → la función es local a cada unidad de traducción; evita conflicto de símbolos al linkear cuando `matmul_morton_avx2.c` y `matmul_morton_omp.c` incluyen el mismo header.

## 7. Fallback ijk

```c
if ((m_block % MR) != 0 || (n_block % NR) != 0) {
    /* zero C, then ijk fallback in double precision via A_local */
    kernel_base_morton_avx2_ijk_fallback(...);
    return;
}
```

Para hojas cuyas dimensiones **no** alinean al tile del microkernel ($m_{\text{block}} \bmod \text{MR} \neq 0$ o $n_{\text{block}} \bmod \text{NR} \neq 0$). En el sweep regular del proyecto $m$ es potencia de 2 con $m \geq 4$ y $n = 128 = 8 \cdot \text{NR}$, así que el fallback **nunca se invoca**. Existe por seguridad: si alguien instancia el kernel con $m = 12$ o $n = 24$, la rutina no produce basura — solo se vuelve lenta.

A diferencia del microkernel optimizado, el fallback indexa por `A_local` (que está row-major gracias a `materialize_a_panel`), lo que mantiene el código de la hoja unificado sin re-implementar el acceso Morton.

## 8. Diferencias con `tiled_ikj_avx2` (Fase 1.4)

| | `tiled_ikj_avx2` | `matmul_morton_avx2` |
|---|---|---|
| Microkernel | 6×16 (12 YMM acc) | 4×16 (8 YMM acc) |
| Estrategia de bloqueo | Tiling explícito KC/MC | Recursión cache-oblivious |
| Tamaño de bloque | $M_c = 192$, $K_c = 384$ fijos | Sub-bloques de cualquier $2^p$, hasta threshold |
| Reorganización de A | No (acceso row-major directo) | Sí (Morton-de-bloques una vez) |
| Tunable principal | $\text{BS} = K_c$ runtime | `g_recursion_threshold_avx2` runtime |
| GFLOPS típico m=1024 single-core | ~57 | menor (más overhead de recursión) |

El `tiled_ikj_avx2` es **más rápido** en single-core porque su loop nest BLIS Goto-style con bloques anclados al hardware del 4600H está más cerca del límite teórico. La ventaja del Morton aparece cuando el problema excede claramente L3 — la recursión multi-nivel se adapta sin requerir re-tuning de los $M_c, K_c$.

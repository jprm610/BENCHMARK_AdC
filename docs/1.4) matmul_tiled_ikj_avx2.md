# `matmul_tiled_ikj_avx2` — Resumen conceptual

## 1. Idea general

La multiplicación de matrices tiene dos problemas independientes:

- **Problema de cómputo**: el procesador hace una operación por ciclo si usás aritmética escalar.
- **Problema de memoria**: aunque tengas AVX2, si los datos vienen de RAM el procesador espera 300+ ciclos por dato.

`matmul_tiled_ikj_avx2` los ataca con dos estrategias apiladas:

| Estrategia | Resuelve | Herramienta |
|---|---|---|
| Tiling | traer datos a cache antes de usarlos | loops `kk`, `ic`, `jr`, `ir` |
| Register blocking | consumir esos datos a máxima velocidad | microkernel AVX2 + FMA |

Ninguna funciona bien sin la otra.

---

## 2. AVX2 y SIMD

**SIMD** (Single Instruction, Multiple Data): una instrucción opera sobre varios datos en paralelo.

Los registros **YMM** de AVX2 tienen 256 bits → caben **8 floats** por registro. El Zen 2 tiene **16 registros YMM** (`ymm0`–`ymm15`).

**FMA** (Fused Multiply-Add): `c = a * b + c` en una sola instrucción (`vfmadd231ps`). Con AVX2 eso son 8 FMAs simultáneas. El Zen 2 tiene 2 unidades FMA → techo teórico de **32 flops/ciclo** por core.

Los intrinsics son funciones de C que mapean 1:1 a instrucciones de hardware:

```c
__m256 a  = _mm256_broadcast_ss(&escalar);    // replicar 1 float en 8 lanes
__m256 b0 = _mm256_loadu_ps(&B[p * ldb]);     // cargar 8 floats de memoria
__m256 c0 = _mm256_fmadd_ps(a, b0, c0);       // c0 = a*b0 + c0  (8 FMAs)
```

## 3. Hiperparámetros

### MR = 6 y NR = 16 — geometría del microkernel (hardware-dictated)

Determinados por la cantidad de registros YMM disponibles:

```
(MR × 2) + 2 + 1 ≤ 16
   ↑         ↑   ↑
acumuladores B   A (broadcast)

→ MR ≤ 6.5  →  MR = 6
```

NR = 16 porque cada fila tiene 16 floats = 2 registros YMM. Con MR=6 y NR=16 se usan exactamente **15 de 16 registros**.

### MC = 192 — bloque de filas (cache-dictated, L2)

El panel de A activo tiene tamaño MC × KC:

```
192 × 384 × 4 bytes = 288 KiB  →  cabe en L2 (512 KiB)
```

MC debe ser múltiplo de MR (192 = 32 × 6).

### KC = 384 — profundidad del panel (configurable, L1d)

El panel de B activo tiene tamaño KC × NR:

```
384 × 16 × 4 bytes = 24 KiB  →  cabe en L1d (32 KiB)
```

Es el único parámetro tunable en runtime (`matmul_tiled_ikj_avx2_set_bs(bs)`). El valor óptimo se encuentra empíricamente barriendo el rango válido y midiendo GFLOPS.

### Resumen

| Parámetro | Valor | Lo fija | Apunta a |
|---|---|---|---|
| MR | 6 | geometría del ISA | registros YMM |
| NR | 16 | geometría del ISA | registros YMM |
| MC | 192 | tamaño del L2 | L2 (512 KiB) |
| KC | 384 | tamaño del L1d | L1d (32 KiB) |

## 4. Loop nest

El orden `kk → ic → jr → ir` es BLIS Goto-style. Cada loop controla una dimensión distinta:

```
for kk in [0, k_dim, KC=384):          ← rodaja de k, panel B a L1d
  kc = min(KC, k_dim - kk)             ← tamaño real del bloque (tail)

  for ic in [0, m, MC=192):            ← bloque de filas, panel A a L2

    for jr in [0, n, NR=16):           ← bloque de columnas, panel B en L1d
                                          (mismo panel reutilizado MC/MR=32 veces)
      for ir in [ic, ic+MC, MR=6):     ← micro-tile de C
        kernel_avx2_tiled_6x16(...)    ← C[6×16] en registros YMM
```

Con `kk` e `ic` fijos, el panel activo de A es **MC × KC** (vive en L2).
Con `kk` y `jr` fijos, el panel activo de B es **KC × NR** (vive en L1d).
Con todos fijos, el microkernel ve **A[MR×KC] × B[KC×NR] → C[MR×NR]**.

El orden `jr` externo / `ir` interno es deliberado: el panel B de L1d se reutiliza MC/MR=32 veces antes de cambiar.

### Manejo de tails

```c
const size_t m_aligned = (m / MR) * MR;  // parte que entra exacto en el microkernel
const size_t n_aligned = (n / NR) * NR;
```

Las filas/columnas sobrantes van a `kernel_avx2_tiled_residual_rows` (máximo MR-1=5 filas). En el proyecto con `n=128` el tail de columnas nunca ocurre.

## 5. Microkernel `kernel_avx2_tiled_6x16`

Recibe un tile de C[6×16] y acumula `A[6×kc] × B[kc×16]` sobre él.

### Fase 1: cargar C en registros (una sola vez)

```c
__m256 c00 = _mm256_loadu_ps(&C[0 * ldc + 0]);  // fila 0, cols 0..7
__m256 c01 = _mm256_loadu_ps(&C[0 * ldc + 8]);  // fila 0, cols 8..15
// ... hasta c50, c51  (12 registros YMM en total)
```

El tile 6×16 se parte en 12 vectores porque cada registro YMM tiene 8 floats y cada fila tiene 16 floats → 2 registros por fila × 6 filas = 12.

### Fase 2: loop kc (el trabajo real)

Por cada paso `p`:

```c
__m256 b0 = _mm256_loadu_ps(&B[p * ldb + 0]);   // fila p de B, cols 0..7
__m256 b1 = _mm256_loadu_ps(&B[p * ldb + 8]);   // fila p de B, cols 8..15

a = _mm256_broadcast_ss(&A[0 * lda + p]);        // A[0,p] replicado en 8 lanes
c00 = _mm256_fmadd_ps(a, b0, c00);               // c00 += A[0,p] * B[p, 0..7]
c01 = _mm256_fmadd_ps(a, b1, c01);               // c01 += A[0,p] * B[p, 8..15]
// ... idem filas 1..5  (12 FMAs por paso p)
```

Por cada paso `p`: 12 FMAs × 8 floats = **96 floats de C actualizados** con solo 2 loads de B y 6 broadcasts de A. C nunca toca memoria.

### Fase 3: guardar C de vuelta (una sola vez)

```c
_mm256_storeu_ps(&C[0 * ldc + 0], c00);
// ... hasta c51
```

### Balance de registros en el loop

```
c00..c51  →  12 YMMs  (acumuladores de C, viven todo el loop kc)
b0, b1    →   2 YMMs  (fila de B, se renuevan cada p)
a         →   1 YMM   (broadcast de A, se reutiliza entre las 6 filas)
─────────────────────
           15 de 16 registros YMM usados
```

---

## 6. Por qué `static inline`

Si el microkernel fuera una función normal en un `.c` separado, al cruzar el boundary de función el compilador tendría que respetar el ABI: guardar los 12 acumuladores YMM al stack antes de la llamada y recargarlos al retornar (**spill**).

El spill es costoso porque el stack vive en memoria:

```
sin inline:  12 stores + 12 loads por invocación  (~240 ciclos de overhead)
con inline:  nada — los 12 YMMs nunca salen de los registros
```

- **`inline`** → el compilador pega el código directamente en el loop `ir`, los acumuladores viven en registros durante toda la pasada kc.
- **`static`** → la función es local a cada unidad de traducción, evita conflicto de símbolos al linkear cuando dos `.c` incluyen el mismo header.

## 7. `kernel_avx2_tiled_residual_rows`

Fallback para las filas/columnas que no entran exacto en el microkernel (máximo MR-1=5 filas).

La diferencia crítica: **C no vive en registros**. El load y store de C están dentro del loop `p`:

```c
for (i = 0; i < mr_eff; i++) {
    for (p = 0; p < kc; p++) {
        __m256 c = _mm256_loadu_ps(&C[i * ldc + j]);  // load en cada p
        c = _mm256_fmadd_ps(a_vec, b, c);
        _mm256_storeu_ps(&C[i * ldc + j], c);          // store en cada p
    }
}
```

No se puede hacer register-blocking porque el número de filas es variable en runtime — no podés hardcodear acumuladores `__m256` para un número desconocido de filas.

Es ~3× más lento pero maneja ≤5 filas sobre miles → impacto negligible.

| | Microkernel normal | `residual_rows` |
|---|---|---|
| C en registros | sí (load/store: 1 vez) | no (load/store: kc veces) |
| Filas | fijas: 6 | variables: 1..5 |
| Columnas | fijas: 16 | variables: cualquier n |
| Tail escalar | nunca | si n % 8 != 0 |
| Velocidad relativa | máxima | ~3× más lento |

# Resumen: `matrix_utils`

## Contexto general

`matrix_utils` es el módulo de soporte del proyecto — maneja ciclo de vida y utilidades de las matrices. No hace cómputo numérico. Es independiente de todos los kernels y no cambia a medida que se añaden optimizaciones.

---

## `scalar_t` y tipos

Todo el proyecto usa `typedef float scalar_t`, definido en `matrix_utils.h`. El tipo `float` son 4 bytes (IEEE 754 single precision), lo que significa 16 floats por línea de caché y 8 floats por registro AVX2. Usar un `typedef` centralizado permite cambiar a `double` tocando una sola línea.

Como `scalar_t` es el tipo fundamental del que dependen todos los módulos, lo más limpio es definirlo en `matrix_utils.h` y que los demás headers lo hereden incluyéndolo:

```
matrix_utils.h        ← define scalar_t
      ↑
matmul_naive.h        ← incluye matrix_utils.h
      ↑
matmul_tiled.h, matmul_avx2.h, ...
```

Esto evita dependencias circulares y pone el tipo donde conceptualmente pertenece: junto con las utilidades de manejo de memoria que lo usan directamente.

Los índices y tamaños usan siempre `size_t` (64 bits) porque para `m = 2^15`, el producto `m * m * sizeof(float)` ya desborda un `int` de 32 bits.

---

## Funciones del módulo

| Función | Propósito |
|---------|-----------|
| `xalloc_aligned(n)` | Aloja memoria para `n` elementos de la matriz, garantizando que el primer elemento quede al inicio de una línea de caché. |
| `xfree(ptr)` | Libera la memoria de una matriz alocada con `xalloc_aligned`. |
| `init_matrix_random(M, rows, cols, seed)` | Llena la matriz `M` de `rows × cols` con valores pseudoaleatorios reproducibles, escalados para estabilidad numérica. |
| `init_matrix_zero(M, rows, cols)` | Llena la matriz `M` de `rows × cols` con ceros. Útil para validar que $A \cdot 0 = 0$. |
| `init_matrix_identity(M, n)` | Llena la matriz cuadrada `M` de $n \times n$ con la identidad. Útil para validar que $I \cdot B = B$. |
| `matrices_close(ref, test, n, abs, rel, ...)` | Compara dos matrices elemento a elemento para verificar que dos kernels producen el mismo resultado dentro de una tolerancia. |

## `xalloc_aligned` — alineación de 64 bytes

La memoria RAM es un arreglo plano de bytes. La caché opera en **líneas de 64 bytes**: cuando la CPU accede a cualquier dirección, el controlador trae el bloque de 64 bytes alineado que la contiene — siempre desde un múltiplo de 64, nunca desde el byte exacto pedido.

`aligned_alloc(64, rounded)` garantiza que el bloque empiece en una dirección múltiplo de 64. El resultado es que `M[0]` cae al inicio de una línea, y todas las líneas subsiguientes están perfectamente alineadas:

```
Línea 0: [ M[0]  ... M[15]  ]
Línea 1: [ M[16] ... M[31]  ]
Línea 2: [ M[32] ... M[47]  ]
```

Sin alineación, `M[0]` podría estar a mitad de una línea, desperdiciando parte de cada transferencia. La alineación también es requisito de las instrucciones AVX2 (`_mm256_load_ps`).

El truco de redondeo:

```c
size_t rounded = (bytes + 63u) & ~((size_t)63u);
```

Redondea `bytes` hacia arriba al próximo múltiplo de 64 — requisito de `aligned_alloc`. Funciona en dos pasos:

1. `bytes + 63u` — garantiza que si `bytes` no era múltiplo exacto, suba al rango del siguiente.
2. `& ~63u` — pone a cero los 6 bits menos significativos, truncando al múltiplo de 64 hacia abajo.

Ejemplos:

| `bytes` | `+ 63` | `& ~63` | resultado |
|---------|--------|---------|-----------|
| 100     | 163    | 128     | 128 ✓     |
| 64      | 127    | 64      | 64 ✓      |
| 65      | 128    | 128     | 128 ✓     |
| 1       | 64     | 64      | 64 ✓      |

## `init_matrix_random` — LCG y escalamiento espectral

### El generador LCG

```c
static unsigned int lcg_next(unsigned int *state) {
    *state = (*state) * 1664525u + 1013904223u;
    return *state;
}
```

Un **Generador Lineal Congruencial** — la forma más simple de generador pseudoaleatorio:

$$\text{estado}_{n+1} = a \cdot \text{estado}_n + c \pmod{2^{32}}$$

con `a = 1664525` y `c = 1013904223` (parámetros de *Numerical Recipes*). El módulo $2^{32}$ es implícito — el desbordamiento de `unsigned int` está bien definido en C (a diferencia del desbordamiento de `int` con signo, que es comportamiento indefinido). Por eso los literales llevan sufijo `u`.

No es aleatorio — es completamente determinístico. La misma semilla produce la misma secuencia en cualquier plataforma. Eso es una decisión de diseño: **reproducibilidad sobre entropía real**. Para un benchmark necesitas que dos kernels reciban exactamente las mismas matrices.

El puntero `unsigned int *state` es necesario porque C pasa argumentos por valor. Sin el puntero, cada llamada recibiría la misma copia del estado y produciría siempre el mismo número.

### El escalamiento $1/\sqrt{m}$

```c
scalar_t scale = (scalar_t)(1.0 / sqrt((double)rows));
M[i * cols + j] = u * scale;
```

El fundamento teórico viene del **Corolario 4.4.7 de Vershynin** (*High-Dimensional Probability*, 2018): para una matriz aleatoria $m \times m$ con entradas subgaussianas de parámetro $v$:

$$\|A\| \leq Cv\sqrt{m} \quad \text{con alta probabilidad}$$

Para entradas en $[-v, v]$ esto implica $\|A\| = \Theta(v\sqrt{m})$. Imponiendo $\|A\| = O(1)$ se recupera $v = 1/\sqrt{m}$.

La consecuencia práctica: la **norma espectral** de $A$ determina cuánto se amplifica $B_i$ en cada iteración:

$$\|B_i\| \leq \|A\|^i \cdot \|B_0\|$$

Sin escalamiento, con $\|A\| = \Theta(\sqrt{m})$ y $I = 2m/n$ iteraciones, los valores crecen como $(\sqrt{m})^{2m/n}$ — overflow garantizado para $m$ mediano. Con el escalamiento la norma queda en $\Theta(1)$ y la recurrencia es numéricamente estable.

En principio se podría recuperar el resultado real multiplicando por $(\sqrt{m})^I$ al final, pero ese factor mismo desbordaría `float` para $m$ grande. Para el proyecto no importa: el objetivo es medir rendimiento, no producir un resultado útil.

## `xfree` — liberación segura

```c
void xfree(scalar_t *ptr);
```

Wrapper sobre `free` que tolera `NULL`. Sin él, liberar un puntero nulo sería comportamiento indefinido en algunas plataformas. Su propósito es uniformizar el ciclo de vida: todo lo que se aloja con `xalloc_aligned` se libera con `xfree`, sin condiciones adicionales en el caller.

---

## `init_matrix_zero` — inicialización a cero

```c
void init_matrix_zero(scalar_t *M, size_t rows, size_t cols);
```

Pone `rows * cols` elementos en cero usando `memset`. Es la forma más rápida de inicializar un bloque de memoria — el sistema operativo y el hardware tienen rutas optimizadas para escrituras de cero. Se usa principalmente en validación: multiplicar `A` por una matriz de ceros debe producir ceros, y cualquier desviación indica un bug.

---

## `init_matrix_identity` — inicialización a identidad

```c
void init_matrix_identity(scalar_t *M, size_t n);
```

Llena la matriz cuadrada `M` ($n \times n$) con la identidad: primero pone todo en cero con `init_matrix_zero`, luego recorre la diagonal poniendo unos en `M[i*n + i]`. Se usa en validación: multiplicar cualquier matriz `B` por la identidad debe devolver `B` sin cambios.

---

## `matrices_close` — tolerancia mixta

```c
scalar_t tol = abs_tol > rel_tol * mag ? abs_tol : rel_tol * mag;
```

Compara dos buffers elemento a elemento con tolerancia mixta:

$$\text{tol} = \max(\text{abs\_tol},\ \text{rel\_tol} \cdot |r|)$$

Se necesitan ambas porque:

- Solo **tolerancia absoluta**: falla cuando los valores son grandes.
- Solo **tolerancia relativa**: falla cuando los valores son cercanos a cero (división por algo muy pequeño).

No valida que el resultado sea matemáticamente correcto — valida que dos kernels producen el mismo resultado. Las diferencias esperadas entre kernels vienen de la **no-asociatividad del punto flotante**: reordenar sumas da resultados ligeramente distintos, no bugs. Las tolerancias recomendadas para `float` después de varias iteraciones son `abs_tol ≈ 1e-5` y `rel_tol ≈ 1e-4`.

Al encontrar el primer elemento fuera de tolerancia retorna inmediatamente con diagnóstico — reporta el primer fallo, no el peor.

# `tests` — Capa de unit-tests

## Para qué existe esta capa

El proyecto tiene tres niveles de verificación, de más fino a más grueso:

| Capa | Carpeta | Qué prueba | Cuándo falla te dice... |
|---|---|---|---|
| **unit** | [`src/tests/`](../src/tests) | Piezas individuales en aislamiento: utilidades, encoding Morton, microkernels AVX-512 | Exactamente cuál primitiva está rota |
| **validate** (integración algebraica) | [`src/drivers/validate/`](../src/drivers/validate) | Cada algoritmo completo contra invariantes ($A\cdot 0=0$, $I\cdot Z=Z$, linealidad) y cross-check contra `matmul_naive` | El algoritmo diverge — pero no dónde |
| **bench** | [`src/drivers/bench/`](../src/drivers/bench) | Performance (GFLOPS, hardware counters) | Algo se volvió lento; no si es correcto |

Los `validate_*` ya prueban correctitud end-to-end. Los `tests` existen porque cuando algo falla, queremos saber **qué primitiva** está rota, no solo que el resultado final diverge. Una regresión en `morton_encode` aparece en `validate_morton` como "matmul_morton diverge en índice 12345" — ilegible. El test unitario te dice "`morton_encode(3, 5)` devolvió 39 en vez de 39" — accionable.

## Los cuatro binarios

| Binario | Fuente | Cubre | Compilación |
|---|---|---|---|
| `bin/tests/test_matrix_utils` | [`test_matrix_utils.c`](../src/tests/test_matrix_utils.c) | `xalloc_aligned`, `init_matrix_zero`, `init_matrix_identity`, `init_matrix_random`, `matrices_close` | `BASE_CFLAGS` (`-O0 -g`) |
| `bin/tests/test_morton` | [`test_morton.c`](../src/tests/test_morton.c) | `morton_encode`, `morton_decode`, `reorganize_to_morton`, `reorganize_from_morton` | `BASE_CFLAGS` (`-O0 -g`) |
| `bin/tests/test_kernel_avx512_morton` | [`test_kernel_avx512_morton.c`](../src/tests/test_kernel_avx512_morton.c) | Microkernel `kernel_avx512_4x32` de [`kernel_avx512_morton.h`](../src/microkernels/kernel_avx512_morton.h) | `CFLAGS_O3_ZEN5` (`-O3 -march=native`) |
| `bin/tests/test_kernel_avx512_tiled` | [`test_kernel_avx512_tiled.c`](../src/tests/test_kernel_avx512_tiled.c) | Microkernel `kernel_avx512_tiled_6x32` de [`kernel_avx512_tiled.h`](../src/microkernels/kernel_avx512_tiled.h) | `CFLAGS_O3_ZEN5` |

Los microkernels se prueban a `-O3 -march=native` porque son `static inline` y dependen de los intrinsics ZMM; a `-O0` el compilador no emite los FMAs y el test mediría otra cosa. Las demás piezas son código escalar y se prueban a `-O0 -g` para que cualquier fallo aparezca con stack frames legibles.

## Estructura común de cada test

Todos siguen la misma convención de los `validate_*`: una función por sub-test, una bandera global `g_failed`, y `exit(0)` solo si todos pasan.

```c
static void run_check(const char *name, int passed) {
    if (passed) printf("  [OK]   %s\n", name);
    else        { printf("  [FAIL] %s\n", name); g_failed = 1; }
}

int main(void) {
    test_a();
    test_b();
    return g_failed ? EXIT_FAILURE : EXIT_SUCCESS;
}
```

Ningún framework externo (Unity, Criterion). Solo `stdio` + códigos de salida.

## Qué cubre cada test

### `test_matrix_utils`

1. **`xalloc_aligned`** — punteros no nulos, alineados a 64 bytes (línea de caché Zen 5), para tamaños desde 1 hasta $2^{20}$ elementos.
2. **`init_matrix_zero`** — todos los elementos quedan en 0 y el centinela trasero no se toca (no hay overrun).
3. **`init_matrix_identity`** — diagonal en 1, fuera de la diagonal en 0, para $n \in \{1, 4, 16, 33\}$ (incluye un caso no potencia de 2).
4. **`init_matrix_random`** — tres sub-checks:
   - Determinismo: misma seed → mismos bytes en dos llamadas.
   - Sensibilidad al seed: seeds distintos producen contenidos distintos.
   - Rango: $|M_{ij}| \leq 1 / \sqrt{\text{rows}}$ + epsilon de redondeo.
5. **`matrices_close`** — cinco casos: buffers idénticos, diferencia justo en la frontera de `abs_tol`, diferencia apenas mayor (debe poblar los punteros de diagnóstico), tolerancia relativa dominando, y `NULL` en los punteros de diagnóstico (no debe crashear).

### `test_morton`

1. **Tabla 4×4** — los 16 valores de `morton_encode` contra el documento técnico.
2. **Round-trip** — $\forall (i, j) \in [0, 64)^2$: $\text{morton\_decode}(\text{morton\_encode}(i, j)) = (i, j)$.
3. **Contiguidad de cuadrantes** — para $m = 8$, etiquetar cada cuadrante (TL, TR, BL, BR) y verificar que `reorganize_to_morton` los empaqueta en cuatro segmentos consecutivos.
4. **Round-trip de reorganización** — para $m \in \{16, 64, 256\}$: row-major → Morton → row-major reproduce el original bit-a-bit.

### `test_kernel_avx512_morton`

El microkernel 4×32 acumula $C \mathrel{+}= A \cdot B$ con 8 acumuladores ZMM. Cuatro tests con $k_c$ creciente:

1. **$k_c = 1$, smoke test** — $A$ = columna de unos, $B$ = fila con valores distintos conocidos. Cada fila de $C$ debe quedar igual a $B$.
2. **$k_c = 8$, aleatorio** — Comparar contra referencia ijk en `double`.
3. **$k_c = 128$, aleatorio** — Tamaño representativo de hoja en `matmul_morton_avx512`.
4. **$k_c = 1024$, stress** — 1024 cadenas FMA por lane; verifica que el error FP32 no explota.

Tolerancias: $\text{abs\_tol} = 10^{-5}$, $\text{rel\_tol} = 10^{-4}$. El error FP32 acumulado crece como $\sqrt{k_c} \cdot \epsilon_{\text{mach}}$; en $k_c = 1024$ vale $\sim 2 \cdot 10^{-6}$, muy por debajo del techo.

### `test_kernel_avx512_tiled`

Espejo exacto del anterior, pero para el microkernel 6×32 de `kernel_avx512_tiled.h` (12 acumuladores ZMM, usado por `matmul_tiled_ikj_avx512` y `matmul_tiled_ikj_omp`). Los mismos cuatro casos con MR = 6, NR = 32.

La referencia es la misma idea — un `ijk` en `double` — pero **acumula** en $C$ (en vez de sobreescribir), porque el microkernel del tiled acumula. Los tests cargan $C$ a cero antes para que la primera acumulación sea equivalente a una escritura limpia.

## Cómo correrlos

```bash
make tests                       # los cuatro, en orden, abortando al primer fallo
make test_matrix_utils           # solo el de las utilidades
make test_morton                 # solo el de Morton
make test_kernel_avx512_morton   # solo el del microkernel 4x32
make test_kernel_avx512_tiled    # solo el del microkernel 6x32
```

`make validate` ahora depende de `tests`: si una primitiva está rota, no se llega a correr los algoritmos completos.

Los binarios quedan en `bin/tests/` (separados de `bin/bench/bench_*` y `bin/validate/validate_*`) y se borran con `make clean`.

---

## Cuándo añadir tests aquí

- **Nueva utilidad en `core/`** — agregar un test a `test_matrix_utils.c` o crear un test propio si el módulo es grande.
- **Nuevo microkernel** — crear `test_kernel_<name>.c` calcado de los dos existentes (smoke + 3 random con $k_c$ creciente).
- **Cambio en la convención de bits Morton** — actualizar la tabla 4×4 de `test_morton.c`.

**Cuándo NO añadir tests aquí.** Si lo que quieres verificar es que un algoritmo completo da el resultado correcto, eso va en `src/drivers/validate/<algo>.c` (invariantes algebraicos + cross-check contra `matmul_naive`), no aquí. La capa de unit-tests es para piezas que `validate_*` no puede aislar.

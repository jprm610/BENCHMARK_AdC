# Análisis: `matmul_morton_omp`

## Base

Se construye directamente sobre `matmul_morton_avx2`: misma recursión Z-order, mismo microkernel 4×16, mismo layout Morton-de-bloques (tile = MR = 4), mismas ramas overwrite / `_add`. Lo único que agrega es paralelismo con **OpenMP tasks** y un **scratch pool per-thread**.

El contraste con `tiled_ikj_omp` (Fase 1.5) es importante: aquel paraleliza un loop `for` rectangular con `#pragma omp for schedule(static)`; este paraleliza una **recursión irregular** con `#pragma omp task`.

---

## Por qué tasks y no `for`

La recursión Morton no tiene un loop rectangular evidente que partir entre threads. En cada nivel, los cuatro sub-productos del caso MK tienen distintas dependencias:

- $C_{\text{top}} = A_{TL} B_{\text{top}}$ y $C_{\text{top}} \mathrel{+}= A_{TR} B_{\text{bot}}$ **deben ejecutarse en orden** (el segundo acumula sobre el primero).
- $C_{\text{bot}} = A_{BL} B_{\text{top}}$ y $C_{\text{bot}} \mathrel{+}= A_{BR} B_{\text{bot}}$ idem.
- Pero **top y bottom son independientes**: $C_{\text{top}}$ y $C_{\text{bot}}$ son segmentos disjuntos de $C$.

OpenMP tasks expresan exactamente esa estructura: lanzas una task para "la secuencia top" y otra para "la secuencia bottom", esperas a las dos, y dentro de cada task la sub-secuencia se ejecuta sin paralelizarse de nuevo.

`#pragma omp for` no podría expresar esto sin re-aplanar la recursión a un loop rectangular, lo que perdería la propiedad cache-oblivious.

---

## Estructura de paralelismo

```c
#pragma omp parallel default(shared)
{
    #pragma omp single
    matmul_morton_omp_inner(...);     /* la recursión arranca aquí */
}
```

- **`parallel`** crea el team de threads una sola vez por llamada al wrapper.
- **`single`** garantiza que solo **un** thread arranca la recursión raíz. Los demás threads del team se quedan en idle esperando tasks que ese thread vaya generando con `#pragma omp task`.

Dentro de la recursión, cada nivel decide si genera tasks:

```c
const int spawn = (m_block * k_block * n_block > g_parallel_threshold_omp);

if (spawn) {
    #pragma omp task default(shared) firstprivate(...)
    mk_top_pair(...);
    #pragma omp task default(shared) firstprivate(...)
    mk_bot_pair(...);
    #pragma omp taskwait
} else {
    mk_top_pair(...);
    mk_bot_pair(...);
}
```

`mk_top_pair` y `mk_bot_pair` son helpers que encapsulan la secuencia (overwrite seguida de `_add`) sobre el mismo segmento de $C$ — quedan como tasks atómicas y la lectura del sitio de spawn permanece limpia.

---

## Las directivas y qué hace cada una

| Directiva | Rol |
|---|---|
| `#pragma omp parallel` | **Fork** — crea el team de threads una sola vez por llamada al wrapper. |
| `#pragma omp single` | Asigna la ejecución de la recursión raíz a **un único thread**. Los demás se quedan disponibles para ejecutar tasks. |
| `#pragma omp task` | Encola una task en la cola global. Cualquier thread idle del team la puede tomar. |
| `#pragma omp taskwait` | Suspende el thread actual hasta que todas las tasks hijas spawneadas en este nivel hayan terminado. |
| `firstprivate(...)` | Copia los valores capturados en el momento del spawn — necesario porque las variables locales (offsets, halves) cambian entre llamadas recursivas. |

---

## Los dos thresholds

`matmul_morton_omp` tiene **dos** thresholds runtime-tunables, distintos:

```c
extern size_t g_recursion_threshold_omp;   /* default 524288 */
extern size_t g_parallel_threshold_omp;    /* default 524288 */
```

| Threshold | Decide |
|---|---|
| `g_recursion_threshold_omp` | A qué tamaño la recursión cae al **leaf kernel** (idéntico al de la Fase 1.7). |
| `g_parallel_threshold_omp` | A qué tamaño la recursión deja de **spawnear tasks** y recursa inline. |

**Default iguales (524288)**: tasks se generan en todos los niveles arriba del leaf, ninguna en el leaf. Esa es la regla más simple — el costo de crear una task (~1 µs) tiene que amortizarse sobre el trabajo que esa task hace; un task a nivel de leaf trabajaría ~10 µs y el overhead sería del 10%.

Subir `g_parallel_threshold_omp` por encima del leaf threshold reduce el número de tasks generadas: la recursión hace algunas divisiones secuenciales antes de empezar a paralelizar. Útil cuando hay pocos threads disponibles. Bajarlo (incluso a 0 — caso permitido) fuerza recursión **totalmente secuencial** desde este módulo — útil para medir el costo del scaffolding OMP aislado del paralelismo real.

## Scratch pool per-thread

El leaf necesita un buffer `A_local` para materializar el panel de $A$ desde el layout Morton-de-bloques. En la versión single-threaded (Fase 1.7) ese buffer se aloja una vez en el wrapper y se pasa a la recursión. En multi-thread no se puede compartir: dos hojas concurrentes lo sobreescribirían mutuamente.

```c
const int max_threads = omp_get_max_threads();

scalar_t **scratches = malloc(max_threads * sizeof(scalar_t *));
for (int t = 0; t < max_threads; ++t)
    scratches[t] = xalloc_aligned(side * side);

#pragma omp parallel default(shared)
{
    #pragma omp single
    matmul_morton_omp_inner(..., scratches);
}
```

En el leaf:

```c
int tid = omp_get_thread_num();
kernel_base_morton_omp(..., scratches[tid]);
```

`omp_get_max_threads` devuelve **cota superior** del team. El array `scratches` se aloja con esa capacidad y cada thread indexa su propio buffer. Con 12 threads lógicos y un panel de $64 \times 64$ (16 KiB), el costo total es ~192 KiB — despreciable.

---

## Por qué no se paralelizan los cuatro sub-productos del caso MK

Los **cuatro** productos del split MK no se pueden lanzar como cuatro tasks paralelas porque dos de ellos (TR y BR) acumulan sobre lo que ya escribió otro (TL y BL respectivamente). Lanzarlos sin sincronización produciría carreras de escritura sobre $C$.

La solución es **agruparlos en dos pares secuenciales**:

| Task | Secuencia interna |
|---|---|
| `mk_top_pair` | TL (overwrite) → TR (accumulate sobre TL) |
| `mk_bot_pair` | BL (overwrite) → BR (accumulate sobre BL) |

Y como top y bottom son disjuntos en $C$, los dos pares **sí** pueden ejecutarse en paralelo. Después del `taskwait`, las cuatro contribuciones están integradas.

Para el caso N el problema no existe: las dos mitades de $n$ son completamente disjuntas — dos tasks paralelas sin dependencia interna.

---

## Topología y configuración recomendada (Ryzen 5 4600H)

```bash
OMP_NUM_THREADS=6 OMP_PLACES=cores OMP_PROC_BIND=close
```

**Why `close` aquí y `spread` en tiled_omp:**

- En `tiled_ikj_omp` (Fase 1.5) cada thread trabaja sobre filas distintas de $A$ y $C$; el reuso de cache **entre threads** es nulo. `spread` distribuye threads entre los 2 CCX para que cada uno tenga su propio L3 de 4 MiB.
- En `matmul_morton_omp`, las tasks que ejecutan `mk_top_pair` y `mk_bot_pair` trabajan **sobre el mismo $A_{TL}/A_{TR}$ o $A_{BL}/A_{BR}$**, así que comparten líneas de A en cache. `close` mantiene los threads dentro del mismo CCX para que ese L3 compartido sea útil.

Empíricamente: `close` escala bien hasta 3 threads (un CCX entero), luego carga el L3 y pierde eficiencia; `spread` escala más pero paga Infinity Fabric por traer líneas cross-CCX.

**6 threads, no 12**: el Ryzen tiene 6 cores físicos con SMT. Para un kernel FMA-bound, poner 2 threads en el mismo core no duplica throughput — compiten por las mismas 2 unidades FMA.

---

## Diferencias con `tiled_ikj_omp` (Fase 1.5)

| | `tiled_ikj_omp` | `matmul_morton_omp` |
|---|---|---|
| Mecanismo OMP | `omp for schedule(static)` | `omp task` + `taskwait` |
| Estructura de loops | Loop nest rectangular | Recursión Z-order |
| Granularidad | $M_c = 192$ rows × T threads | Una task por split arriba del threshold |
| Scratch | Ninguno (kernel directo) | Pool per-thread, indexado por `omp_get_thread_num` |
| Sync | Barrera implícita al final del `omp for` | `taskwait` explícito en cada split |
| Binding óptimo | `spread` | `close` |
| Single para residuos | Sí (filas no múltiplo de MR) | No (no hay residuos, $m$ pot. de 2) |

El `tiled_ikj_omp` es **más rápido** porque sus loops rectangulares son naturalmente paralelos y el overhead de OMP es mínimo. `matmul_morton_omp` paga overhead de tasks pero gana flexibilidad cache-oblivious.

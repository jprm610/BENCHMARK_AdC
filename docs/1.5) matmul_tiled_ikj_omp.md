# Análisis: `matmul_tiled_ikj_omp`

## Base

Se construye directamente sobre `matmul_tiled_ikj_avx2`: mismo microkernel 6×16, mismo tiling jerárquico (KC/MC/MR/NR), mismos `static inline` en `kernel_avx2_tiled.h`. Lo único que agrega es paralelismo con OpenMP.

---

## Estructura de paralelismo

```c
memset(C, 0, ...);          // secuencial — fuera de la región paralela

#pragma omp parallel        // fork: crea el team de threads UNA sola vez
{
    for (pp = 0; pp < k; pp += KC) {        // todos los threads recorren esto
        #pragma omp for schedule(static)    // divide el loop ic entre threads
        for (ic = 0; ic < m_aligned; ic += MC) {
            // cada thread trabaja en su rango de filas de C
            ...kernel_avx2_tiled_6x16(...)
        }
        // ← barrera implícita: todos esperan antes del siguiente pp

        if (m_aligned < m) {
            #pragma omp single { residual_rows(...) }
            // ← barrera implícita al salir
        }
    }
}                           // join: los threads mueren aquí
```

---

## Las tres directivas y qué hace cada una

| Directiva | Rol |
|---|---|
| `#pragma omp parallel` | **Fork** — crea el team de threads. Solo se ejecuta una vez por llamada a la función. |
| `#pragma omp for schedule(static)` | **Divide** el rango de `ic` entre los threads existentes. No crea threads nuevos. |
| `#pragma omp single` | Ejecuta el bloque con **un solo thread**; los demás esperan. Tiene barrera implícita al salir. |

---

## Por qué `parallel` está afuera del loop `pp`

Crear/destruir un team de threads cuesta microsegundos. Si `#pragma omp parallel` estuviera dentro del loop `pp`, el runtime haría fork/join en cada iteración. Al ponerlo afuera, los threads se crean una sola vez y viven durante todo el cómputo.

---

## Por qué `pp` no se paraleliza

Cada iteración de `pp` **acumula** sobre `C`. Si dos threads trabajaran en diferentes valores de `pp` simultáneamente habría write races en `C`. El loop `pp` corre en lockstep para todos los threads; la barrera implícita al final del `omp for` garantiza que todos terminaron de acumular el tile `k` actual antes de avanzar al siguiente.

---

## Por qué `omp single` para las filas residuales

Las filas residuales son como máximo `MR - 1 = 5` filas (las que no llenan un tile completo de 6). Distribuirlas entre 6 threads generaría más overhead de coordinación que trabajo real. Un solo thread las maneja; `omp single` garantiza exclusividad y sincroniza al salir.

**`omp single` vs `omp master`:**
- `single` → lo ejecuta cualquier thread que llegue primero + barrera implícita
- `master` → siempre T0 + sin barrera implícita

Se usa `single` porque importa que solo uno lo haga, no cuál.

---

## Configuración recomendada (Ryzen 5 4600H)

```bash
OMP_NUM_THREADS=6 OMP_PLACES=cores OMP_PROC_BIND=spread
```

- **6 threads, no 12**: el Ryzen tiene 6 cores físicos con SMT (12 CPUs lógicos). Los 2 threads lógicos de un mismo core comparten las unidades FMA. Para un kernel FMA-bound, poner 2 threads en el mismo core no duplica throughput — compiten por el mismo recurso.
- **`OMP_PLACES=cores`**: cada thread se ancla a un core físico, no migra.
- **`OMP_PROC_BIND=spread`**: distribuye los threads entre los 2 CCX del procesador para aprovechar el L3 de cada CCX (4 MiB por CCX).

---

## Cómo sabe OMP cuántos cores usar

Lee `OMP_NUM_THREADS`. Si no está seteada, pregunta al OS cuántos CPUs lógicos hay y usa ese número — que en el 4600H sería 12, subóptimo para este kernel.

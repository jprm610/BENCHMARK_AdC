# Análisis: `matmul_tiled_ikj_omp`

## Base

Se construye directamente sobre `matmul_tiled_ikj_avx512`: mismo microkernel 6×32, mismo tiling jerárquico (KC/MC/MR/NR), mismos `static inline` en `kernel_avx512_tiled.h`. Lo único que agrega es paralelismo con OpenMP.

---

## Estructura de paralelismo

```c
init_matrix_zero(C, m, n);   // secuencial — fuera de la región paralela

#pragma omp parallel         // fork: crea el team de threads UNA sola vez
{
    for (kk = 0; kk < k_dim; kk += KC) {  // todos los threads recorren esto
        #pragma omp for schedule(static)   // divide el loop ic entre threads
        for (ic = 0; ic < m_aligned; ic += MC) {
            // cada thread trabaja en su rango de filas de C
            ...kernel_avx512_tiled_6x32(...)
        }
        // ← barrera implícita: todos esperan antes del siguiente kk

        if (m_aligned < m) {
            #pragma omp single { residual_rows(...) }
            // ← barrera implícita al salir
        }
    }
}                            // join: los threads mueren aquí
```

---

## Las tres directivas y qué hace cada una

| Directiva | Rol |
|---|---|
| `#pragma omp parallel` | **Fork** — crea el team de threads. Solo se ejecuta una vez por llamada a la función. |
| `#pragma omp for schedule(static)` | **Divide** el rango de `ic` entre los threads existentes. No crea threads nuevos. |
| `#pragma omp single` | Ejecuta el bloque con **un solo thread**; los demás esperan. Tiene barrera implícita al salir. |

---

## Por qué `parallel` está afuera del loop `kk`

Crear/destruir un team de threads cuesta microsegundos. Si `#pragma omp parallel` estuviera dentro del loop `kk`, el runtime haría fork/join en cada iteración. Al ponerlo afuera, los threads se crean una sola vez y viven durante todo el cómputo.

---

## Por qué `kk` no se paraleliza

Cada iteración de `kk` **acumula** sobre `C`. Si dos threads trabajaran en diferentes valores de `kk` simultáneamente habría write races en `C`. El loop `kk` corre en lockstep para todos los threads; la barrera implícita al final del `omp for` garantiza que todos terminaron de acumular el tile `k` actual antes de avanzar al siguiente.

---

## Por qué `omp single` para las filas residuales

Las filas residuales son como máximo `MR - 1 = 5` filas (las que no llenan un tile completo de 6). Distribuirlas entre 8 threads generaría más overhead de coordinación que trabajo real. Un solo thread las maneja; `omp single` garantiza exclusividad y sincroniza al salir.

**`omp single` vs `omp master`:**
- `single` → lo ejecuta cualquier thread que llegue primero + barrera implícita
- `master` → siempre T0 + sin barrera implícita

Se usa `single` porque importa que solo uno lo haga, no cuál.

---

## Configuración recomendada (EPYC 9R45)

```bash
OMP_NUM_THREADS=8 OMP_PLACES=cores OMP_PROC_BIND=close
```

- **8 threads**: el EPYC 9R45 en AWS c8a.2xlarge tiene 8 cores físicos. El hypervisor deshabilita SMT, por lo que hay exactamente un CPU lógico por core físico. No hay riesgo de poner 2 threads en el mismo core.
- **`OMP_PLACES=cores`**: cada thread se ancla a un core físico, no migra.
- **`OMP_PROC_BIND=close`**: distribuye los threads de forma contigua. Equivalente a `spread` aquí porque hay un solo nodo NUMA y L3 compartido (32 MiB).

---

## Cómo sabe OMP cuántos cores usar

Lee `OMP_NUM_THREADS`. Si no está seteada, pregunta al OS cuántos CPUs lógicos hay y usa ese número — que en el EPYC 9R45 con SMT deshabilitado son exactamente 8, coincidiendo con los cores físicos.
